## Why

市面上的 AI 行程規劃工具（Funliday、TripJam、去趣 ChicTrip、Wanderlog、Layla、Mindtrip）都有同一個結構性缺陷：行程表由 LLM 直接生成，導致幻覺出不存在的店家、排入公休日、以及用「車程約 40 分鐘」這種估算值取代真實可搭乘的班次。對沒有自駕的旅客而言，一份無法照著走的行程表等於沒有價值。

台灣的交通部 TDX 平台免費開放觀光 POI、停車場、廁所，以及涵蓋公車／台鐵／高鐵／捷運的多模式轉乘規劃 API。國際競品不會去接台灣的班次資料，這是它們拿不到的資料優勢。本專案利用這個優勢，做出一個**行程表由程式驗證過可行、而非由 LLM 生成**的規劃工具。

## What Changes

- 新增對話式行程規劃：使用者以自然語言描述出發地、目的地、日期天數、每日起訖時間與偏好，系統產出逐時段行程。
- 新增「LLM 只做判斷題」的排程引擎：候選召回、地理分群、交通銜接、營業時間與時間可行性驗證一律由程式 deterministic 執行；LLM 僅負責依偏好挑選與排序候選 POI、以及產生行程敘述文字。任何無法通過可行性驗證的行程不得輸出。
- 新增大眾運輸銜接：行程中每一段轉場都附帶 TDX 回傳的真實班次（路線、班次時間、轉乘點、步行段），而非估算車程。
- 新增八大類附近搜尋（美食、飲料、停車場、廁所、景點、飯店、交通運輸、伴手禮），同時作為獨立搜尋功能與行程每一站的內嵌資訊。停車場與廁所與其他類別同級，不降級為次要結果。
- 新增使用者帳號與行程儲存：第三方登入、儲存／取回／刪除已規劃行程。
- 資料存取一律經過 `PoiProvider` / `RoutingProvider` 介面，MVP 僅實作 TDX，排程引擎不得直接依賴任何特定資料來源。

### Non-goals（MVP 明確排除）

- 台灣以外的地區。日本與全球版不在本次範圍，僅以 provider 介面預留擴充點。
- 訂房、訂票、訂位等交易功能。
- 多人協作編輯、旅遊記帳、打包清單、社群分享。
- 付費 API（Google Places／Routes 等）。MVP 必須在免費額度內運作。

## Capabilities

### New Capabilities

- `trip-planning`: 對話式蒐集行程需求，並以 deterministic 排程引擎產出逐時段、通過可行性驗證的多日行程。涵蓋需求解析、候選召回、每日地理分群、LLM 選點、可行性驗證與失敗回退。
- `transit-routing`: 提供兩點間在指定時間的大眾運輸銜接方案，回傳真實班次資訊，並判定該銜接在行程時間窗內是否可行。供 `trip-planning` 驗證轉場之用，行程輸出亦直接呈現其結果。
- `nearby-search`: 依座標與類別查詢附近地點，支援八大類別。同時服務獨立搜尋頁與行程站點的內嵌顯示。
- `trip-library`: 使用者第三方登入，以及已規劃行程的儲存、列出、取回與刪除。

### Modified Capabilities

（無，本專案為全新專案）

## Impact

- **新專案骨架**：Next.js + TypeScript，部署於 Vercel free tier。
- **外部相依**：TDX 觀光資訊資料庫 v2、TDX 公共運輸旅運規劃功能模組、TDX geocoding（皆需 API 金鑰，限 50 req/s per IP）；Gemini API free tier；MapLibre GL JS。
- **機密管理**：TDX 與 LLM 金鑰僅在 Next.js server side 使用，不得進入 client bundle。
- **資料儲存**：免費層資料庫（儲存使用者帳號與行程）。因儲存使用者資料，需納入基本個資處理考量。
- **速率限制**：TDX 50 req/s 為硬限制，排程引擎的候選召回策略必須在此限制內完成一次規劃。
