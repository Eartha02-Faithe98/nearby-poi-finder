## Context

全新專案，無既有程式碼。動機見 proposal.md - Why；行為契約見 specs/。

塑造本設計的三個外部約束：

- **TDX 為 MVP 的主資料來源**，免費，但每個來源 IP 限 50 req/s（實測遠更嚴格）。一次完整的行程規劃必須在此限制內完成。
  spike 後另加入兩個補充來源：環境部公廁開放資料（D8）與 OSM 營業時間（D9）。兩者皆為預抓快照，不在請求路徑上。
- **Vercel free tier 有函式執行時間上限**，而一次規劃涉及多次 TDX 呼叫與至少一次 LLM 呼叫，總時長可能逼近上限。
- **LLM 使用 Gemini free tier**，有每分鐘與每日請求數限制，且輸出不保證穩定。

## Goals / Non-Goals

**Goals:**

- 讓「行程可行性保證」這條規格在架構上不可能被違反，而不是依賴 LLM 自律。
- 讓排程引擎完全不知道資料來自哪裡，使日後加入其他國家的 provider 不需修改引擎。
- 全部跑在免費額度內。

**Non-Goals:**

- 不追求行程「最佳化」。通過可行性驗證且符合偏好即可，不做全域最佳解。
- 不做離線運作、不做即時協作。
- 不在 MVP 實作**第二個國家**的 provider。介面形狀以台灣境內的三個來源（TDX、環境部、OSM）驗證，
  這已足以證明引擎不依賴單一來源。

## Decisions

### D1：四步排程引擎，LLM 只在第三步

```
1. 候選召回      程式    依目的區域與類別，自 PoiProvider 取得候選 POI 集合
2. 地理分群      程式    將候選依座標分群為 N 天，避免單日跨區移動
3. 選點與排序    LLM     於每日候選群中，依使用者偏好挑選與排序
4. 可行性驗證    程式    營業時間、轉場銜接、時間窗總長；不通過則退回第 3 步
```

**理由**：規格要求「MUST NOT 輸出未通過可行性驗證的行程」。若 LLM 直接生成行程，這條規格只能靠事後檢查補救，且 LLM 會產生不存在的地點。將 LLM 的輸出限縮為「從一組真實候選中挑選 ID 並排序」，站點真實性在型別層就成立——LLM 無法回傳不存在的 ID。

**替代方案**：
- *LLM 直接生成完整行程*：所有競品的做法，正是幻覺與不可行行程的來源。否決。
- *LLM 搭配 function calling 自主呼叫 TDX*：LLM 決定呼叫次數，無法預估 TDX 用量，且在 50 req/s 與函式時間上限下不可控。否決。

第 4 步失敗時退回第 3 步重試，**重試次數設上限**（初值 3 次）。超過上限即依規格回報無可行行程，不得無限迴圈。

### D2：Provider 介面即使只有一個實作也要做

定義 `PoiProvider`（依區域與類別取候選、依座標取周邊、地理編碼）與 `RoutingProvider`（兩點間銜接方案、時間窗可行性判定）。MVP 只實作 TDX。

**理由**：這是唯一能讓「日後加入日本」不變成重寫的成本。介面形狀不靠猜——它由第 4 步驗證實際需要的資訊反推（路線識別、實際發車／抵達時間、可行性布林值），任何 provider 只要能提供這些就能接上。

**取捨**：這違反「單一實作不抽象」的一般原則。接受，因為第二個 provider 是已知需求而非臆測需求，且介面由已定義的驗證需求約束，不是憑空設計。

### D3：交通銜接使用 TDX 旅運規劃模組，不自架路徑引擎

**理由**：TDX 已提供多模式轉乘規劃 API，直接回傳含班次的方案。自架 OpenTripPlanner 需 2–8GB RAM，無免費 hosting 可放，等於放棄免費目標。

**spike 結果（2026-09-13，見 spike-notes.md 1.2／1.4）：採用本模組。** 本島市區、本島偏鄉、金門、綠島皆回傳含實際班次時間、路線識別與上下車站名的方案。方案 B（以原始時刻表自行實作銜接判定）未被放棄，但從「全面回退」降級為「澎湖專用補洞方案」。

**採用附帶三項強制條件：**

1. **一律帶 `first_mile_mode=0&last_mile_mode=0`。** 預設值會產生 `drive` 與 `cycle` 接駁段，等於叫沒有車的使用者開車。強制步行後路線品質反而提升，且多個方案才會是真正不同的班次而非同一班次的三種接駁。
2. **澎湖無涵蓋**，以澎湖本島內路線重測確認為真實缺口而非測試誤差。處理方式待定。
3. **路線名稱含錯誤資料**（觀測到台東→綠島的航線被標為「東港—小琉球」），顯示時以上下車站名為主要依據，不單獨信任路線名稱。

### D4：Supabase 同時作為登入與資料庫

**理由**：`trip-library` 需要第三方登入與持久化兩件事，Supabase free tier 一次提供兩者。分別接 auth 服務與資料庫是兩套整合成本，換不到任何東西。

**替代方案**：NextAuth + Neon/Turso——多一層整合，無對應收益。否決。

### D5：對話狀態不落伺服器

多輪對話由客戶端持有完整歷程，每次請求連同歷程送出；規劃 API 維持無狀態。僅「使用者主動儲存的最終行程」寫入資料庫。

**理由**：省掉 session 儲存與清理，也讓未登入使用者能完整使用規劃功能（規格要求）。對話歷程長度有限（數輪），成本可忽略。

### D6：TDX 呼叫預算與快取

候選召回階段**每個目的區域每個類別只打一次 TDX**，取回後於程序內完成篩選，不逐點查詢。TDX 觀光 POI 屬低頻變動資料，於伺服器端加入帶 TTL 的快取；交通銜接查詢與時間相關，不快取。

**理由**：50 req/s 是硬限制。若採「每個候選點各查一次」，單次規劃即可能觸及上限。

**spike 修正（見 spike-notes.md 1.1／1.3／3.3）：**

- ⚠ **真實速率限制是每分鐘 5 次，不是 50 req/s。** 429 回應的標頭寫明
  `x-ratelimit-limit-minute: 5` 與 `retry-after: 40`，且為單一帳號跨所有 API 群的共用額度。
  這與文件宣稱值相差約 600 倍，**推翻了本決策原本的前提**。
- 營業時間**不在**主列表端點內，需另打 `/Attraction/ServiceTime` 與 `/Restaurant/ServiceTime`。所幸這兩支端點的全量資料極小（77 與 90 筆），可一次取回並長期快取。
- 單一縣市的資料量會超過單頁上限（臺南市景點 548 筆 > `$top=500`）。「只打一次」若照字面實作會**靜默截斷**，已改為有上限的分頁。
- `/Nearby` 一次回傳所有類別的集合，因此**多類別的周邊查詢只需一次請求**。但其資料列只有 ID、名稱、座標，沒有地址與類別代碼。

**因應每分鐘 5 次的修正決策：**

一次規劃的可用呼叫數 = 300 秒（Vercel 函式上限）÷ 12 秒 ≈ **25 次**。單一縣市六類的候選召回
加上分頁就可能用掉 10–15 次，再加上逐段轉場查詢，**即時查詢的做法無法在時限內完成一次規劃**。

因此本決策由「限制呼叫次數」改為「**把靜態資料移出請求路徑**」：

1. **POI 資料一律預抓為快照**，比照 D8（公廁）與 D9（OSM）的做法。TDX 觀光 POI 全台僅
   6,228 景點 + 3,624 餐廳 + 15,676 飯店，屬低頻變動資料，適合離線預抓後隨程式碼部署。
2. **即時呼叫只保留給與時間相關的轉場查詢**（`maas/routing`）。這是唯一無法預抓的部分。
3. tasks 3.4 的 TTL 快取因此**不是最佳化，而是可行性的前提**。

**待確認**：本專案的 TDX 帳號是否為較低的會員層級。若可升級至更高額度，上述限制會鬆動，
但架構不需回頭改——預抓快照在任何額度下都更快更穩。

### D7：地圖用 MapLibre GL JS

開源、無授權費、可切換圖磚來源。圖磚供應商在實作時選定免費額度足夠者，不影響架構。

### D8：廁所資料源用環境部開放資料，不用 OSM

`nearby-search` 的八大類中，廁所在 TDX 完全沒有對應資源。改用**環境部「全國公廁建檔資料」**
（`data.moenv.gov.tw/api/v2/fac_p_07`，data.gov.tw dataset 30794）。

**理由**：實測 45,843 列／24,989 個地點，22 縣市全涵蓋（含澎湖 391、金門 353、連江 92），
座標零缺漏，且附無障礙／親子／性別友善／尿布台／清潔等級等屬性。同一範圍的 OSM
`amenity=toilets` 只有 5,833 筆。授權為政府資料開放授權條款，無 ODbL 的 share-alike 義務。

**兩項強制條件**（見 spike-notes A-1）：

1. **只能預抓，不能即時查。** 該 API 的 `limit` 伺服器端硬上限 1000，抓全量需 46 次
   `offset` 分頁、約 2 分鐘，且過程會出現疑似限速的非 JSON 回應。以帶 TTL 的預抓快照供應查詢。
2. **provider 必須依座標聚合。** 男廁／女廁／無障礙各自一列共用同一座標（單點最多 170 列），
   設施型別須收斂為單一地點的屬性，否則附近搜尋會回傳大量重複結果。
   另需以 `taiwan-bounds` 濾掉 0.32% 的座標髒資料。

**替代方案**：*與決策 D9 共用 OSM 單一 provider*——少一個資料源，但筆數只有 1/7.9 且離島涵蓋未經驗證。
以「省一個 provider」換掉 4 萬筆資料不划算。否決。

### D9：OSM 作為營業時間的補充來源

TDX 的結構化營業時間全台僅 77 個景點與 90 家餐廳（spike-notes 1.3），驗證形同虛設。
以 Overpass API 取 OSM 台灣範圍的 `opening_hours`（餐飲 POI 8,776 筆，約 97 倍）補上。

**理由**：`trip-planning` 的可行性驗證要求檢查站點在抵達時間是否營業。TDX 的覆蓋率讓這條
規格在絕大多數站點上無法生效。OSM 覆蓋率約 18%，不完美，但從「形同虛設」變成「多數熱門店家可用」。

**取捨**：OSM 授權為 ODbL，需在介面標示資料出處。與 D8 同理，Overpass 是無 SLA 的免費共享
服務（spike 期間即多次回傳非 JSON），**不得放在使用者請求路徑上**，一律預抓快照。

**POI 比對**：OSM 與 TDX 是兩套獨立 ID，需以名稱與座標鄰近度比對。比對失敗的站點
依 spec 既有規定標註「營業時間未知」，不得臆測。

### D10：澎湖的 RoutingProvider 分流

TDX 旅運規劃模組對澎湖回 0 案（spike-notes 1.2a），但澎湖公車的**原始資料完整存在**
（Route／Stop／Schedule 三支端點皆 200）。因此 `RoutingProvider` 在澎湖走獨立實作：
自原始時刻表判定「這段在時間窗內是否搭得到」。

**理由**：`trip-planning` 的「地理範圍限制」明列離島為支援範圍，且「請求離島行程」
scenario 直接以澎湖為例。放著不處理等於已知會違反規格。

**取捨**：這是全專案唯一一處依地理位置分流的實作。分流點放在 `RoutingProvider` 之內，
排程引擎不感知——引擎仍然只看到「一個 RoutingProvider」，D2 的抽象不被破壞。


### D11：飲料走 OSM，伴手禮走 TDX + OSM 聯集

TDX 收錄的是「觀光餐飲」而非日常店家，八大類中的飲料與伴手禮在其中都沒有乾淨的對應
（spike-notes A-2）。兩類的最佳來源不同，因此分開決定：

**飲料 → OSM。** `shop=beverages|tea|coffee`、`amenity=cafe`、`cuisine` 含 `bubble_tea|coffee_shop`，
去重後 **9,527 筆**，其中手搖飲核心（`shop=beverages` + `cuisine=bubble_tea`）**3,923 筆**。
TDX 的對應代碼全是觀光咖啡館，**手搖飲 0 筆**——台灣最主要的飲料型態在 TDX 中不存在。

**伴手禮 → TDX 代碼集合 ∪ OSM。** TDX 側取餐飲 `CuisineClasses` 116／115／204 與
景點 `AttractionClasses` 14／6／21，語意精準（郭記名點、阿源伯柿餅、宜蘭餅發明館）但量少；
OSM 側取 `shop=gift|confectionery|pastry`（約 1,160 筆）補涵蓋，
**刻意排除 `bakery`（1,489）與 `deli`（725）**——那是一般麵包店與熟食店，不是伴手禮。

**取捨**：這兩類的結果品質會低於景點／美食／廁所。飲料缺營業時間（9,527 筆中僅 2,211 筆有）；
伴手禮混用兩套分類標準。接受，因為替代方案是讓手搖飲整個查不到。

**TDX 代碼的可信度限制**：TDX **不提供代碼表**（`/CuisineClass` 等皆 404，swagger 無 enum），
上述代碼意義是以 2,000 筆樣本實證反推的。代碼是多標籤且彼此重疊（同一家店同時掛多碼）。
實作時必須以測試固定住這份對應，代碼語意若變動要能被測試抓到，不得散落在程式各處硬編碼。


## Risks / Trade-offs

- **TDX 旅運規劃模組涵蓋率不足以支撐離島與偏鄉** → 見 D3：以 spike 作為第一個任務，備有方案 B，在引擎開發前決定。
- ~~**單次規劃超出 Vercel free tier 函式執行時間上限**~~ → **已解除**。spike 1.5 確認 Vercel Hobby 方案在 fluid compute 下的函式時長預設與上限皆為 300 秒，遠高於一次規劃所需。串流進度回報（tasks 7.5）改以使用者體驗為理由保留，不再是逾時的緩解措施。
- **Gemini free tier 的 RPM／RPD 限制導致規劃失敗** → 第 3 步失敗時以明確錯誤回報使用者，不得退化為 LLM 直接生成行程。重試次數上限（D1）同時限制了 LLM 呼叫次數。
- **LLM 回傳不符結構的輸出** → 要求結構化輸出並於伺服器端以 schema 驗證；驗證失敗視同第 3 步失敗，計入重試上限。
- ~~**TDX POI 資料的營業時間欄位大量缺漏**~~ → **已量測並處理**。spike 1.3 確認全台僅 77 個景點與 90 家餐廳有結構化營業時間，缺漏是常態而非例外。以 D9 的 OSM 補充來源緩解（8,776 筆，約 97 倍）；仍比對不到的站點依規格標註「營業時間未知」。
- ⚠ **TDX 每分鐘 5 次的額度使即時查詢的規劃流程不可行** → 見 D6 的修正：POI 改為預抓快照，即時呼叫只留給轉場查詢。此風險在 spike 階段（3.3 實作時）才被發現，因為文件宣稱的數值錯了兩個數量級。
- **補充資料源為無 SLA 的免費服務** → Overpass 在 spike 期間多次回傳非 JSON，環境部 API 分頁時亦然。兩者皆以預抓快照供應（D8／D9），使用者請求路徑上不存在這個相依，快照過期時服務降級而非失敗。
- **儲存使用者行程涉及個資** → MVP 僅儲存第三方登入回傳的識別資訊與行程內容，不蒐集額外個資；資料隔離由規格的「使用者資料隔離」要求約束。

## Open Questions

spike 發現四件會改動 spec 的事實（詳見 spike-notes.md 的「待決事項」）。**四件皆已裁示完畢。**

**仍待專案擁有者決定（2026-09-14，不阻擋實作）：**

- **TDX 帳號的會員層級能否升級。** 實測額度為每分鐘 5 次（見 spike-notes 3.3）。
  已由 D6 的快照架構吸收，不再是架構問題，但影響快照重建成本
  （全量預抓約 12 分鐘）與 geocode 的即時可用性。
- **`data/snapshots/`（20.2 MB）是否納入版控。** 不納入就不會被部署，
  快照在正式環境將永遠缺漏。替代方案是改於 CI 建置時產生，但需要 TDX 金鑰與 12 分鐘。

**已裁示（2026-09-13）：**

- **A — 廁所用環境部開放資料；飲料用 OSM；伴手禮用 TDX + OSM 聯集。**
  裁示為「先驗政府開放資料，失敗才回退 OSM」，驗證結果為成立、不需回退：
  環境部「全國公廁建檔資料」45,843 列／24,989 個地點，22 縣市全涵蓋，為 OSM 的 7.9 倍。
  → D8、D11；spike-notes「決策 A 的驗證」。
- **B — 另找資料源補齊營業時間。** OSM 台灣有 8,776 個餐飲 POI 帶 `opening_hours`（TDX 僅 90 家）。→ D9。
- **C — 澎湖單獨走方案 B。** TDX 的澎湖公車路線／站牌／時刻表皆回 200，原始資料完整。→ D10。
- **D — 不需裁示。** 顯示時以上下車站名為主要依據，不單獨信任路線名稱。→ D3 的強制條件。

## Post-MVP 候選

記於此處的是已經討論過、判定不進 MVP、但不應遺忘的方向。不是待辦，是備忘。

### 網路推薦作為「排序訊號」（2026-09-13 提出）

**動機——現行設計最軟的一塊**：TDX 的 6,228 個景點與 3,624 家餐廳**沒有評分、
沒有評論、沒有熱門度**。D1 的第 3 步要 LLM「依偏好挑選與排序」，但它手上只有名稱與
類別，實際上是在瞎猜。這是目前架構裡最缺乏根據的一步。

**界線——存在性與排序必須分開**：
- **存在性 MUST NOT 來自網路推薦。** 部落格、社群、論壇的店家可能已歇業、可能是業配、
  可能是別縣市的同名店。把候選集合換成這種來源，等於把幻覺從 LLM 搬到資料源，
  proposal 的 Why 所批評的競品缺陷會原封不動回到本專案。
- **排序 MAY 參考較軟的來源。** 猜錯的後果只是行程不夠好，不是叫使用者跑去一家不存在的店。

**不進 MVP 的原因**：
1. Google Places 有評分，但 proposal 的 Non-goals 明文排除付費 API。要走這條得先改 proposal。
2. 免費的網路抓取在 Vercel free tier 上不可靠：反爬、內容非結構化、需 LLM 抽取（而
   Gemini free tier 有 RPM／RPD 限制），且抓回的內容仍須與 TDX 的 POI 做名稱＋座標比對
   ——即 D9 已知不易的那件事。
3. 會同時牽動 proposal 的 Non-goals、`domain.ts` 的 `Poi` 型別（需加評分欄位）與 D1
   第 3 步的輸入。在 provider 尚未完成時改資料模型，代價高於做完再加。


## Migration Plan

全新專案，無既有系統需遷移。部署至 Vercel，金鑰以環境變數管理，僅於 server side 讀取。
