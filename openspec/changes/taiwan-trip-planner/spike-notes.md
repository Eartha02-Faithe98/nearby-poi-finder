## 1.5 Vercel free tier 函式執行時間上限

**日期**：2026-09-13
**來源**：Vercel 官方文件 `/docs/functions/configuring-functions/duration`（last_updated 2026-08-24）

Vercel Functions 在 fluid compute（預設啟用）下的時長限制：

| 方案 | 預設 | 最大 | 延長上限 |
|---|---|---|---|
| **Hobby（免費）** | **300s** | **300s** | — |
| Pro | 300s | 800s | 1800s（Beta） |
| Enterprise | 300s | 800s | 1800s（Beta） |

**結論**：Hobby 方案有 300 秒可用，且為預設值，無需額外設定。

**對 design.md 的影響**：原先列為風險的「單次規劃超出 Vercel free tier 函式執行時間上限」在
300 秒的額度下不再是實質限制——一次規劃的 TDX 呼叫加 LLM 呼叫遠低於此。已下修該風險條目。

**保留的事項**：
- tasks 7.5 的串流進度回報仍保留。理由已非避免逾時，而是使用者體驗——數十秒的等待需要
  回饋。此外文件指出 HTTP/1.1 的長連線可能被中介層關閉，建議在工作進行時串流進度或
  心跳資料，這也支持保留串流。
- Next.js App Router 設定方式為在 route 檔案匯出 `export const maxDuration = <秒>`。

## 1.1 TDX 帳號與 API 金鑰 — 完成

**日期**：2026-09-13。金鑰由專案擁有者申請並填入 `.env.local`。

- 認證端點：`POST https://tdx.transportdata.tw/auth/realms/TDXConnect/protocol/openid-connect/token`
  （`grant_type=client_credentials`）。token 效期 **86400 秒（24 小時）**。
- 驗證呼叫：`GET /Attraction?$top=3` → **HTTP 200，3 筆非空資料**。

### 重要：網路上流傳的端點全部是舊的

各教學文章與部落格寫的 `https://tdx.transportdata.tw/api/basic/v2/Tourism/ScenicSpot/{City}`
**一律回 404**。實際情況：

| 項目 | 正確值 |
|---|---|
| 觀光 API base | `https://tdx.transportdata.tw/api/tourism/service/odata/V2/Tourism` |
| 景點資源名 | `Attraction`（`ScenicSpot` 已retire） |
| 轉乘規劃 base | `https://tdx.transportdata.tw/api/maas` |
| 公共運輸 base | `https://tdx.transportdata.tw/api/basic`（此 base 仍有效，公車等） |

OpenAPI 定義檔的真實位置是 `https://tdx.transportdata.tw/webapi/File/Swagger/V3/{swaggerId}`
（swagger UI 頁面本身是 SPA，直接抓會得到 HTML 外殼）。已知 id：
觀光 `0aed433a-9e95-404d-974c-4e70e29ae460`、旅運規劃 `4513f9d6-caae-4cf7-a50c-e7887bec804e`。

### 觀光 API 實際提供的資源（共 26 條路徑）

`Nearby`、`Attraction`、`AttractionFee`、`Restaurant`、`Hotel`、`TourismServiceSite`、
`Trail`、`TrailFacility`、`CyclingRoute`、`CyclingRouteFacility`、`Event`，
以及各自的 `/{ID}` 與部分的 `/ServiceTime`。

`Nearby` 端點參數：`X`(經度)、`Y`(緯度)、`Distance`(公尺，**上限 1000**)。

`Attraction` 的欄位包含 `VisitDuration`（建議停留時間）與 `ParkingInfo`、`Facilities`，
對行程規劃有直接價值。

### 速率限制的實測

文件宣稱 50 req/s，但實測在**數秒內連續 6 個請求**即回 429。
`$top` 上限低於 20000（回 400）。實作時必須遠比 50 req/s 保守，並處理 429 重試。

## 1.2 TDX 旅運規劃模組涵蓋率 — 完成

**端點**：`GET https://tdx.transportdata.tw/api/maas/routing`

**必填參數共五個**：`origin`、`destination`、`transit`、**`gc`**、**`top`**。
（2026-09-13 實作 3.2 時補正：本節原先漏記 `gc` 與 `top`，缺任一個即回
`HTTP 400 {"error":{"code":20001,"msg":"\"gc\" is required"}}`。）

| 參數 | 說明 |
|---|---|
| `origin` / `destination` | `lat,lng`，Decimal Degree |
| `transit` | **無中括號**的逗號整數列（swagger 描述寫 `[3,4,5,6,7,8,9]` 是錯的，`example` 的 `3,4,5,6,7,8,9` 才對）。運具代碼 `3`高鐵 `4`台鐵 `5`公車 `6`捷運 `7`輕軌 `8`渡輪 `9`纜車 `20`航空 |
| `gc` | 0.0–1.0。**`gc=1` 時間最短、`gc=0` 價格最便宜。** 本專案以可行性為先，用 `gc=1` |
| `top` | 回傳路線數，預設 5、最大 10。數量越多運算越久 |
| `depart` / `arrival` | `yyyy-mm-ddTHH:mm:ss`，台北時區，二擇一 |
| `first_mile_mode` / `last_mile_mode` | `0`走路 `1`腳踏車 `2`開車 `3`共享單車。**swagger 宣稱預設為 0，但實測不指定時會產生 drive／cycle 區段——不可信任此預設值**，見下方（b） |
| `transfer_time` | `{min},{max}` 分鐘，預設 15~60 |

swagger 定義檔 id：`4513f9d6-caae-4cf7-a50c-e7887bec804e`。

### 涵蓋率實測（2026-09-19 09:00 出發）

| 情境 | 路線 | 結果 |
|---|---|---|
| 本島市區 | 台南車站→安平古堡 | ✓ 3 案，Bus 2 臺南火車站(北站)→安平古堡(安北路) |
| 本島偏鄉 | 瑞穗車站→瑞穗牧場 | ✓ 3 案，HighwayBus 1137／1142 瑞穗→掃叭頂 |
| 離島 金門 | 金城→金湖 | ✓ 3 案，Bus 5往沙美 金城站→瓊林圓環 |
| 離島 綠島 | 台東富岡漁港→綠島 | ✓ 3 案，Ferry 臺東（富岡）─綠島 09:30→10:20 |
| **離島 澎湖** | **馬公市區→跨海大橋** | **✗ 0 案** |

回傳含實際班次時間、路線名稱、上下車站名——`transit-routing` spec 要求的欄位皆齊備。

### 三個必須處理的缺陷

**（a）澎湖完全無涵蓋。** 初測用的目的地座標落在望安島（需船班），可能構成偽陰性，
故以澎湖本島內的「馬公市區→澎湖跨海大橋」重測，**仍為 0 案**。確認為真實缺口。

**（b）預設會回傳開車與腳踏車接駁。** 未指定時 `first_mile_mode`／`last_mile_mode`
會產生 `drive`、`cycle` 區段，等於叫沒有車的使用者開車 900 公尺。
**必須明確指定 `first_mile_mode=0&last_mile_mode=0`。**
額外收穫：強制步行後路線品質反而提升——台南案從 Bus 14→文平路 變成 Bus 2→安平古堡(安北路)，
且三個方案不再是同一班次的三種接駁，而是真正不同的班次。

**（c）TDX 回傳的路線名稱存在錯誤資料。** 綠島案的方案 #2／#3 路線名為
「東港—小琉球」，但起訖站是「台東富岡漁港 → 綠島南寮漁港」。名稱與實際航線不符。
若直接顯示，會叫使用者去搭一艘不存在的船——這對「真實班次」這個核心賣點是直接打擊。
實作時路線名稱不可全然信任，應以上下車站名為主要顯示依據。

## 1.3 觀光 POI 營業時間缺漏比例 — 完成

**已確認**：營業時間**不在**主列表端點內。`/Attraction`、`/Restaurant`、`/Hotel`
的 `ServiceTimeInfo` 欄位在 500 筆抽樣中 **100% 為空**。
營業時間另有獨立端點 `/Attraction/ServiceTime` 與 `/Restaurant/ServiceTime`，
資料結構良好（`ServiceDays` 星期陣列 + `StartTime`/`EndTime`），可直接解析。

**關鍵數字**：以 `$top=500` 查詢兩支 ServiceTime 端點，分別只回
**77 筆（景點）**與 **90 筆（餐廳）**。因回傳筆數遠低於 `$top`，這應即為全台灣的完整筆數。

**總筆數已取得**（2026-09-13 補測，`$top=500` + `$skip` 分頁，每頁間隔 9 秒）：

| 資源 | 全台總筆數 | 有結構化營業時間 | 覆蓋率 |
|---|---|---|---|
| `/Attraction` | 6,228 | 77 | **1.24%** |
| `/Restaurant` | 3,624 | 90 | **2.48%** |
| `/Hotel` | 15,676 | 無 ServiceTime 端點 | — |

**結論：營業時間驗證在 98% 以上的站點上無法生效。** 已由 design D9（OSM 補充來源）處理。

**分頁的實作限制**（供 3.2 的 HTTP 客戶端參考）：
- `$top` 上限依端點而異。列表端點可用 500；**`/ServiceTime` 端點 `$top=1000` 即回 400**，需用 500。
- 即使每頁間隔 9 秒，6,228 + 3,624 + 15,676 筆的分頁過程仍出現 3 次 429 與 1 次連線逾時。
  重試必須同時接住非 200 **與 fetch 拋出的例外**，只處理前者會讓整個流程中斷。

## 1.4 D3 決策 — 完成

**決策：採用 TDX 旅運規劃模組。**

理由：本島市區、本島偏鄉、金門、綠島四種情境皆回傳含實際班次時間、路線識別與上下車
站名的方案，完全滿足 `transit-routing` spec 的欄位要求。自行以原始時刻表實作銜接判定
（方案 B）在這四種情境下不會更好，只會更貴。

**但決策附帶三項強制條件**，皆源自 1.2 的缺陷：

1. 所有查詢一律帶 `first_mile_mode=0&last_mile_mode=0`，不得使用預設值。
2. 澎湖需要獨立處理。MVP 的處理方式尚未決定，須與專案擁有者確認——見下方「待決事項」。
3. 路線名稱不可全然信任，顯示時以上下車站名為主。

**方案 B 未被完全放棄**：它從「全面回退」降級為「澎湖專用的補洞方案」。

### A. 八大類別中有四類在 TDX 觀光 API 中沒有對應資源

`nearby-search` spec 的「類別涵蓋範圍」需求要求八類同等支援，但實際資料來源是：

| 類別 | 資料來源 | 狀態 |
|---|---|---|
| 景點 | `/Attraction` | ✓ |
| 美食 | `/Restaurant` | ✓ |
| 飯店 | `/Hotel` | ✓ |
| 交通運輸 | `api/basic` 各運具端點 | ✓ |
| 停車場 | `api/basic/v1/Parking/OffStreet/CarPark/City/{City}` | ✓ 回 200，回應結構待確認 |
| 飲料 | 疑為 `Restaurant.CuisineClasses` 之一種代碼 | ✗ 未確認 |
| 伴手禮 | 疑為 `Restaurant.CuisineClasses` 或 `AttractionClasses` 之一種代碼 | ✗ 未確認 |
| **廁所** | **在 TDX 中找不到任何資源** | **✗ 缺** |

類別代碼皆為數字（如 `AttractionClasses: [3, 2, 16]`、`CuisineClasses: [2, 254, 116]`），
swagger 未附代碼表，需另尋 TDX 代碼查詢服務才能對應到中文名稱。

廁所是先前討論中明確列為差異化重點的類別之一，TDX 無此資料。

### B. 營業時間驗證在絕大多數站點上無法生效

見 1.3。`trip-planning` spec 的「行程可行性保證」要求驗證站點在抵達時間是否營業，
並允許資料缺漏時標註為未知。實測顯示「未知」會是常態而非例外。

### C. 澎湖無轉乘規劃

見 1.2（a）。`trip-planning` spec 的「地理範圍限制」明列離島為支援範圍，
且「請求離島行程」scenario 以澎湖為例。

### D. TDX 路線名稱存在錯誤資料

見 1.2（c）。影響 `transit-routing` spec 的「班次資訊真實性」需求。

## 決策 A 的驗證（2026-09-13）

專案擁有者裁示：**先驗政府開放資料，失敗才回退 OSM**。驗證結果為**成立，不需回退**。

### A-1. 廁所資料源 — 政府開放資料驗證通過 ✓

先前記錄的「`data.gov.tw` REST API 路徑失敗（Method not allowed）」是**路徑猜錯，不是 API 不存在**。

| 項目 | 正確值 |
|---|---|
| data.gov.tw metadata API | `GET https://data.gov.tw/api/v2/rest/dataset/{datasetId}` |
| 公廁資料集 id | **30794**（「全國公廁建檔資料」，環境部） |
| 實際資料 API | `GET https://data.moenv.gov.tw/api/v2/fac_p_07` |
| API 金鑰 | metadata 的 `resourceDownloadUrl` 內含一支政府發布的共用 key，但共用即共用配額，本專案改為自行註冊並以 `MOENV_API_KEY` 提供（2026-09-18 裁示） |
| 授權 | 政府資料開放授權條款第 1 版（無 share-alike） |

data.gov.tw **沒有公開的搜尋 API**（`/api/front/dataset/search`、`/api/v1/rest/search`、
`/api/v2/rest/search` 皆 404）。只能以已知 datasetId 查 metadata。

環境部平台的 API 金鑰檢查發生在 dataset id 驗證**之前**——亂編的 id 也回同樣的
「api_key 不存在」，故無法用錯誤訊息反推 id 是否正確。id 正確性是以
`https://data.moenv.gov.tw/dataset/detail/fac_p_07` 的頁面標題確認的。

#### 全量實測（45,843 筆）

| 指標 | 數值 |
|---|---|
| 總筆數 | **45,843**（`number` 欄位全部唯一） |
| **不重複座標點** | **24,989** |
| 縣市涵蓋 | **22 個全到** |
| 澎湖／金門／連江 | 391／353／92 |
| 座標欄位為空或 0 | **0** |
| 名稱／地址為空 | 0／0 |

對照 OSM 的 `amenity=toilets` 5,833 筆，政府資料為其 **7.9 倍**，且離島皆有涵蓋。

欄位：`county` `areacode` `village` `number` `name` `address` `administration`
`latitude` `longitude` `grade` `type2` `type` `exec` `diaper`。

型別分布：女廁所 16,000／男廁所 15,693／無障礙廁所 7,373／混合廁所 4,524／
親子廁所 1,353／性別友善廁所 892／未設定 8。尿布台（`diaper=1`）4,393 筆。
清潔等級（`grade`）：特優級 44,808／優等級 840／不合格 137／普通級 58。

#### 三個必須處理的實作條件

**（a）`limit` 伺服器端硬上限 1000，需 `offset` 分頁。**
指定 `limit=100000` 只回 1000 筆，且只涵蓋 7 個縣市——**看起來像離島沒資料，其實是被截斷**。
抓全量需 46 次請求、約 2 分鐘。分頁期間出現數次非 JSON 的錯誤回應（疑似限速），
呼叫端需重試。此成本只能以**預抓快取**吸收，不得放在使用者請求路徑上。

分頁參數為 `offset`（官方文件 `https://data.moenv.gov.tw/paradigm` 確認）。
未指定 `sort` 時回傳順序不穩定，驗證分頁是否生效時必須同時指定 `sort`，否則會誤判為無效。

**（b）0.32% 座標髒資料。** 148 筆落在台灣 bbox 外，其中 47 筆為經緯度顛倒、
101 筆為其他錯值（例：臺北市士林區的店家標成 `lng=21.52`）。
以既有的 `taiwan-bounds` 過濾即可，不需特別處理顛倒值。

**（c）一個地點被拆成多列建檔。** 男廁／女廁／無障礙廁所各自一列，
共用同一組座標與地址。45,843 列實為 24,989 個地點，單一座標最多 **170 列**。
PoiProvider **必須依座標聚合**，將 `type`／`diaper`／`grade` 收斂為單一地點的屬性，
否則附近搜尋會回傳大量同座標的重複結果。

### A-2. 飲料與伴手禮的 TDX 類別代碼 — 無乾淨對應 ✗

**TDX 不提供代碼表。** `/CuisineClass`、`/AttractionClass`、`/Class` 皆 404；
觀光 API 的 swagger（`0aed433a-9e95-404d-974c-4e70e29ae460`）中
`CuisineClasses` 與 `AttractionClasses` 僅宣告為 `array of int32`，**沒有 enum**。
POI 本身也沒有任何文字類別欄位。

改以實證反推：抽樣 2,000 筆 `Restaurant` 與 2,000 筆 `Attraction`，依代碼分群檢視名稱。

`Restaurant.CuisineClasses`（n = 該代碼出現次數）：

| 代碼 | n | 樣本 | 判讀 |
|---|---|---|---|
| 116 | 187 | 佳樂蛋糕、郭記名點、素寶齋肚臍餅 | **伴手禮**（糕餅名產） |
| 115 | 73 | 阿源伯柿餅、野薑花粽、北埔陳記仙草 | **伴手禮**（地方特產加工） |
| 204 | 5 | 尚好堅果、葉記炒花生 | **伴手禮**（農特產） |
| 103 | 105 | 愛上咖啡、二泉湖畔咖啡館 | 飲料（咖啡館） |
| 102 / 98 / 99 | 76 / 58 / 119 | 同上，與 103 大量重疊 | 飲料（咖啡館，界線不明） |
| 101 | 93 | 賴媽媽豆花、天下奇冰館 | 甜點冰品，非飲料 |
| 254 / 2 / 1 | 595 / 375 / 329 | 客家菜、餐館 | 一般餐飲，最大宗 |

`Attraction.AttractionClasses` 中與伴手禮相關者：`14` 觀光工廠（金門酒廠、宜蘭餅發明館、

**兩個結論：**

1. **代碼是多標籤且彼此重疊。** 同一家店同時掛多個代碼（例：「愛上咖啡」同時為 103 與 98，
   「6號花園」為 1／102／106）。無法建立一對一對應，只能以**代碼集合近似**。
2. **手搖飲料店完全不在 TDX 範圍內。** TDX 收錄的是「觀光餐飲」，不是日常店家。
   台灣最主要的飲料型態在此資料源中不存在。

因此 `nearby-search` spec 的「八類同等支援」在 TDX 單一資料源下**無法成立**，
飲料需另尋資料源。

## 3.2 實作 TDX HTTP 客戶端時的實機發現（2026-09-13）

單元測試以假 fetch 驗證重試與 token 換發，但以下三件事只有打真 API 才會現形。
記於此處，供後續 provider 實作參考。

**（a）觀光 API 回的是 OData 信封，不是裸陣列。**
`/Attraction?$top=3&$format=JSON` 回傳 `{ "value": [...] }`。
即使指定 `$format=JSON` 亦然。解包已收進客戶端的 `getList()`，
provider 不需各自處理——spike 階段的三支指令稿曾各寫了一遍。
但並非所有端點都包信封，`getList()` 兩種形狀都接。

**（b）`maas/routing` 的必填參數比 1.2 原本記載的多。** 見 1.2 的參數表補正。
缺 `gc` 或 `top` 即回 400，錯誤碼 `20001`。

**（c）TDX 的 4xx 會在 body 裡說明原因。**
例：`{"result":"fail","error":{"code":20001,"msg":"\"gc\" is required"}}`。
客戶端若只記狀態碼，這個唯一的線索就消失了——（b）正是靠把 body 納入錯誤訊息才發現的。
客戶端已將 body 截斷後納入錯誤訊息。

**重試策略的依據**：429 與 5xx 重試（退避加倍）；連線層例外同樣重試
（spike 期間 `tdx.transportdata.tw` 出現過 `UND_ERR_CONNECT_TIMEOUT`，
第一版計數腳本只接住非 200，因此整個流程中斷）；其餘 4xx 立即失敗，
因為那是請求本身的問題，重試只會消耗速率額度。認證請求適用同一套策略，
但金鑰被拒（4xx）不重試。

## 3.3 實作 PoiProvider 時的實機發現（2026-09-13）

### ⚠ TDX 的真實速率限制是「每分鐘 5 次」，不是 50 req/s

先前記載的「數秒內 6 個請求即 429」現在有了確切解釋。429 回應的標頭直接寫明：

```
ratelimit-limit: 5          ratelimit-remaining: 0
ratelimit-reset: 40         retry-after: 40
x-ratelimit-limit-minute: 5 x-ratelimit-remaining-minute: 0
```

**每分鐘 5 次，與文件宣稱的 50 req/s 相差約 600 倍。**

**這是單一帳號的共用額度，不分 API 群。** 實測依序呼叫 tourism → basic → basic → maas
三個不同 base，同一個計數器從 3 遞減到 0。maas 的回應另帶 `x-ratelimit-limit: 144000`
（疑為日額度），但每分鐘 5 次才是實際的約束條件。

**對設計的衝擊**（需更新 design D6 與風險評估）：

- 一次規劃的可用呼叫數 = 300 秒（Vercel 上限）÷ 12 秒 ≈ **25 次**。
- 候選召回若走即時查詢，單一縣市六類加分頁就可能用掉 10–15 次；
  再加上每段轉場各一次路線查詢，**單次規劃無法在 Vercel 的函式時限內完成**。
- 結論：**快取（tasks 3.4）不是最佳化，是可行性的前提。** POI 屬低頻變動資料，
  應比照 D8／D9 的做法預抓為快照；即時呼叫只保留給與時間相關的轉場查詢。
- 待確認：本專案的 TDX 帳號是否為較低的會員層級。若可升級，上述限制會鬆動。

客戶端已改為：預設節流間隔 12.5 秒（對應每分鐘 4.8 次），且 429 時**依伺服器的
`retry-after` 等待**而非自行猜測——原本 1+2+4+8 秒共 15 秒的指數退避，
在伺服器要求等 40 秒的情況下必然重試耗盡失敗（實機已重現）。

### `/Nearby` 一次回傳所有類別，但欄位極少

`GET /Nearby?X={經度}&Y={緯度}&Distance={公尺}`。**不接受任何 OData 參數**
（`$top`、`$format` 皆回 400）。`Distance` 上限 1000。

回傳單一物件，內含 24 個 `Related*` 集合：`RelatedAttractions`、`RelatedRestaurants`、
`RelatedHotels`、各式車站（Bus／InterCityBus／Metro／ThsrRail／TraRail／Airport／Port／Bike）、
以及六種停車場（City／Tourism／Port／RailStation／Freeway／Airport）。

**多類別的周邊查詢因此只需一次請求**——這在每分鐘 5 次的額度下極為關鍵。

但**每筆只有 ID、名稱、座標**，沒有地址、沒有營業時間、**沒有類別代碼**。
因此伴手禮無法由 `/Nearby` 過濾，需另循類別代碼查詢。

### OData 查詢能力

| 能力 | 結果 |
|---|---|
| `$filter=contains(PostalAddress/City,'臺南市')` | ✓ 可用 |
| `$filter=contains(AttractionName,'安平古堡')` | ✓ 可用 |
| `$filter=CuisineClasses/any(c: c eq 116)` | ✓ 可用（單一條件） |
| `$filter=...any(c: c eq 116 or c eq 115)` | ✗ **HTTP 500**，必須一碼一次查詢 |
| `$spatialFilter=nearby(lat,lon,dist)` | ✗ 不支援 |
| `$top` | 500 安全；1000 在 `/ServiceTime` 等端點回 400 |

### 沒有 geocoding 端點

`/api/basic/v2/Map/GeoCode` 與 `/api/maas/geocoding` 皆 404。
地點名稱解析須自行以名稱搜尋組成：觀光 POI 走 `contains()`，
台鐵車站則全量取回（約 240 站，一次請求）後本地比對。

### 「台」與「臺」：縣市名要正規化，POI 名稱不可以

實測 `/Attraction` 的名稱中**含「台」252 筆、含「臺」225 筆**，兩種寫法都大量存在
（台灣戲劇館、台塑企業文物館 vs 文臺寶塔、臺紅茶葉文化館）。

- **縣市名**：`PostalAddress/City` 一律用「臺」，使用者輸入須正規化，否則「台南市」查無結果。
- **POI 名稱**：**不可正規化**。把「台灣戲劇館」改寫成「臺灣戲劇館」會讓它永遠查不到。
  實作採「先以字面查詢，無結果時才試另一種寫法」，在稀缺額度下只在必要時多花一次。

### 單一縣市的資料量超過單頁上限

臺南市的景點實測 **548 筆**，超過 `$top=500`。design D6 原寫「每個區域每個類別只打一次」，
若照字面實作會**靜默截斷** 48 筆。已改為有上限的分頁（上限 10 頁）。

|---|---|---|

**結論：按需載入即足夠，不做切分。** 關鍵不在總量，而在單次查詢只碰 1–2 份快照

實機驗證（對真實快照）：六份全部載入 1,074 ms，**快取後重讀 0.29 ms**
（公廁快照首次 488 ms）。

### 過期的處理方式：警告而非拋錯

`loadSnapshot` 的行為分兩類，理由不同：

- **缺漏、損毀、rowCount 與實際筆數不符** → **拋錯**，訊息含該快照對應的
  `npm run prefetch:*` 指令。靜默回空會讓「還沒預抓」看起來像「這個範圍查無結果」，
  而 `nearby-search` spec 要求查無結果必須是可信的告知。
- **過期**（預設 30 天）→ **不拋錯**，但在回傳值標記 `stale` 並發出警告。
  資料舊的後果是「某家店已歇業卻仍列出」，規格對此已有規定（標註營業時間未知、
  由使用者自行確認）；為此讓整個服務不可用並不合理。但它必須被說出來。

`rowCount` 的唯一用途是偵測截斷——被截斷的快照看起來完全正常，只是悄悄少了一部分台灣。

### 部署設定

快照以 `fs` 於執行期讀取，而 Next.js 的檔案追蹤只納入它能從 import 推導的相依，
以路徑字串讀取的檔案推導不到。因此 `next.config.ts` 需要：

```ts
outputFileTracingIncludes: { "/api/**": ["./data/snapshots/**"] }
```

**尚未於實際部署驗證**——目前還沒有任何 API route（tasks 4.1）。先寫是因為漏掉它
會變成只在正式環境出現的錯誤，事後很難聯想到原因。

### tsconfig 的一項調整

預抓指令稿以 Node 原生的 TypeScript 支援執行，而 Node 不做副檔名解析，
import 必須明寫 `.ts`／`.mts`；`tsc` 預設禁止這種寫法。因此開啟
`allowImportingTsExtensions`（`noEmit` 已為 true，符合該旗標的前提）。
這是讓指令稿能重用 `src/` 既有程式碼的代價——否則就得再抄一份認證與重試邏輯。

## 3.9 OSM 營業時間比對的實測結果（2026-09-16）

### `opening_hours` 解析——不裝套件，寫子集

9,558 個帶 `opening_hours` 的 OSM 地點共 4,545 種不同寫法。以子集文法實測：

| 文法 | 涵蓋率 |
|---|---|
| 星期選擇器 + `HH:MM-HH:MM` + `;` 分隔 + `off` | 90.1% |
| 再加「逗號也可能分隔規則」與忽略 `PH`／`SH` | 95.6% |
| **實作最終值** | **9,133 / 9,558 = 95.6%** |

解不掉的 425 筆是 `"10"`、`"12hr"`、`"營運12小時"`、`"open"`、`"五、六、日 18:00-24:00"`
這類自由文字，**完整文法的 `opening_hours` 套件同樣解不出來**——換一個相依換不到那 4.4%。
故不引入相依。解不掉時整串視為未知，不做部分解析。

兩個實作上非拿掉不可的細節：

- **`25:00`–`48:00` 的延伸時刻是正式寫法**，實測 70 筆在用（`Mo-Su 16:00-25:00`）。
  與 `11:00-03:00` 同義，兩者若不等義，同一家店會因為店家怎麼填而得到不同結果。
- **逗號同時用於「時段並列」與「規則並列」**（`Mo-Fr 09:00-21:30,Sa-Su 10:00-22:00`）。
  以「後一段是否以星期開頭」區分，這一條就值 5.5 個百分點。

### 比對命中率——D9 的實際效益遠低於預期

名稱正規化（去空白、台→臺、去括號標點、小寫）後比對 tdx-food + tdx-attraction 共 9,828 筆：

| 半徑 | 名稱完全相同的命中 | 多於一個候選 |
|---|---|---|
| 50 m | 337 (3.4%) | 4 |
| 200 m | 376 (3.8%) | 5 |
| 500 m | 437 (4.4%) | 9 |
| 5 km | 474 (4.8%) | 20 |

放寬到「名稱互相包含」（200 m 內）另外命中 299 筆，抽樣檢視皆為同一家店——
差異幾乎都是分店名與副標題（`龍情花生軟糖(龍潭總店)` ⇄ `龍情花生`）。
**取 200 m + 完全相同優先、互相包含次之**：再放寬換來的多是同名連鎖店的風險，
而套錯營業時間比沒有營業時間更糟（會通過可行性驗證，然後讓使用者吃閉門羹）。

全量套用的結果：

| 快照 | 筆數 | 取得營業時間 |
|---|---|---|
| tdx-food | 3,622 | 145（4.0%） |
| tdx-souvenir | 1,041 | 31（3.0%） |
| tdx-attraction | 6,206 | 23（0.4%） |
| tdx-hotel | 15,672 | 7（0.0%） |
| **合計** | 26,541 | **206（0.8%）** |

景點與飯店本來就不在 OSM 快照的查詢範圍內（`amenity=restaurant|cafe|fast_food|ice_cream`、
`shop=beverages|tea|coffee|bakery|confectionery|pastry|gift`），那兩列的低命中是預期內的。
**真正的數字是餐飲側的 3.8%**（176 / 4,663）。

**這比 D9 的預期低很多。** D9 的理由是「TDX 的營業時間覆蓋率 1.24%／2.48% 形同虛設，
OSM 有 8,776 筆可補」——但那 8,776 筆多半是 TDX 收藏之外的店家，兩個集合的交集很小。
補完之後，TDX 餐飲 POI 的營業時間覆蓋率從 2.48% 升到約 6%，仍然是「多數未知」。

**開放問題（已於 2026-09-17 裁示，見 design D12：加入附近搜尋、不進入行程規劃）**：
要不要讓 OSM 成為餐飲類的**第一級 POI 來源**
（像 D11 對飲料所做的），而不只是替 TDX 補欄位？OSM 有 52,910 筆餐飲 POI、
9,558 筆帶營業時間，直接當來源可用的營業時間會多兩個數量級。
代價是 ODbL 的出處標示範圍擴大，且與 TDX 結果需要去重（tasks 3.12 已排）。
在裁示之前，3.9 就照 D9 的原意實作為補欄位，行為正確、效益有限。

**建議的裁示時機：3.12（去重）之前，不是現在。** 3.10 與 3.11 本來就要寫「從 OSM 快照
依標籤產出 POI」的讀取器，兩個任務都是它的呼叫者。等那兩個做完，「餐飲也加進來」
就退化成多一組標籤加上 3.12 本來就要做的去重，決定成本從「改 design 與 spec 的出處需求」
降到「加一行標籤」，而且屆時手上會多兩個實測數字：OSM 側的資料品質、以及去重實際撞掉多少。

**若裁示為採用，兩個 capability 的取用策略應該不同**：附近搜尋該全收（使用者在路口找吃的，
52,910 筆遠比 3,622 筆有用），行程規劃則以 TDX 為主、OSM 為補並偏好有營業時間者
（選點需要策展品質，排進巷口便當店不是使用者要的行程）。

### 效能

OSM 52,910 筆建網格索引 89 ms；26,541 個 TDX POI 全部比對完約 670 ms。
以網格分桶取代全比（5.2 億次距離計算），單次查詢只比鄰近 9 格。

## 3.10 飲料類別的 OSM 資料源實測（2026-09-17）

以 design D11 的標籤集合（`amenity=cafe`、`shop=beverages|tea|coffee`、
`cuisine=bubble_tea|coffee_shop`）自 `osm-places` 快照取出：

| 指標 | 數值 |
|---|---|
| 飲料 POI | **8,999**（全快照 52,910 筆中） |
| 帶營業時間 | 2,115（**23.5%**） |
| 篩選耗時 | 48 ms |

D11 記的是 9,527 筆，差額來自快照本身：預抓時已濾除台灣範圍外的座標與無名稱的地點
（無名稱者無法呈現也無法比對）。

手搖飲連鎖的涵蓋（驗證「TDX 手搖飲 0 筆」這個缺口確實被補上）：
清心 361、茶的魔手 158、迷客夏 122、可不可熟成紅茶 103、鮮茶道 91、大苑子 87、
得正 34、龜記 22。鼎泰豐 9 家與麥當勞 399 家皆未被收進飲料。

**兩種標法都必須收。** 同一個連鎖品牌的分店在 OSM 有的標成 `shop=beverages`
（迷客夏、茶的魔手），有的標成 `amenity=cafe` + `cuisine=bubble_tea`（可不可熟成紅茶），
只收一種會讓同品牌的一半分店查不到。

**`cuisine` 有 2,942 筆是分號分隔的多值**（`bakery;coffee_shop`）。只比對整串字面
會讓這些店全部落榜，必須切開比對。

**名稱變體是既有的資料品質限制，不是本任務要解的**：`50嵐` 309 家與 `五十嵐` 17 家
在 OSM 是兩個不同的字串。這只影響「使用者以店名搜尋」的情境（tasks 4.3），
不影響依類別與座標的周邊查詢。

## 3.11 伴手禮的 OSM 側實測（2026-09-17）

TDX 側的代碼集合（`CuisineClasses` 116／115／204、`AttractionClasses` 14／6／21）
在 3.3 已實作，並由 `poi-provider.test.ts` 以等值斷言固定住。本次補的是 OSM 側。

| 來源 | 筆數 | 帶營業時間 |
|---|---|---|
| OSM（`shop=gift|confectionery|pastry`） | 1,037 | 237 |
| TDX（tdx-souvenir 快照） | 1,041 | — |
| 未去重合計 | 2,078 | — |

**排除的 `bakery` 與 `deli` 共 1,426 筆**，與 D11 的裁示一致。收進來會讓「伴手禮」
變成「所有賣吃的店」，使用者要找的名產反而被淹沒。

**兩側在 200 公尺內同名者只有 24 筆（1.2%）。** 這是 3.12 去重的實際規模——
兩個資料源對「伴手禮」的理解幾乎不重疊：TDX 收的是觀光工廠與名產老店，
OSM 收的是被標了 `shop=gift` 的店家。去重要做（同一家店不該出現兩次），
但它不是這個類別的主要問題。

**OSM 側的品質參差，這是已知取捨。** 樣本中「臺灣玻璃館」「允成食品行」合理，
但也有「泉威布丁豆花」「CDPiazza」「Ayoi」這類難以判斷是不是伴手禮的店家。
D11 已記錄「伴手禮混用兩套分類標準，品質低於景點／美食／廁所」，實測確認如此。
改善需要的是店家層級的判斷，不是標籤層級的篩選——超出 MVP 範圍。

## 3.12 兩資料源去重的實測（2026-09-17）

去重沿用 3.9 的比對器（名稱正規化 + 200 公尺網格索引），不另寫一套：同一個問題
（這兩筆是不是同一家店）只該有一個答案。呼叫順序是**先補營業時間、再去重**——
OSM 那一筆的營業時間已經搬到 TDX 那一筆上，捨棄的只有重複，不是資訊。

以合併後的實際結果驗證（design D12 裁示後）：

| 類別 | TDX | OSM | 去重後 | 濾掉的重複 | 帶營業時間 | 耗時 |
|---|---|---|---|---|---|---|
| 美食 | 3,622 | 41,688 | 44,829 | 481 | 6,639（**14.8%**） | 602 ms |
| 伴手禮 | 1,041 | 1,037 | 2,056 | 22 | 260（12.6%） | 165 ms |

**營業時間覆蓋率從 4.0% 升到 14.8%**，這是 D12 的實質效益——不是因為比對變準了，
而是因為那 9,558 筆有營業時間的 OSM 店家終於自己進到結果裡，不必再等 TDX 有同一家店。

**保留 TDX 那一筆、捨棄 OSM 那一筆**：TDX 的名稱與地址是策展過的，而營業時間已經搬過去。
反過來做會拿到 `Dori 烘培坊` 這種缺地址的名稱。

**同名但超過 200 公尺的不併**：連鎖店在同一條街有兩家分店是常態，併掉會把使用者
導到比較遠的那一家。
